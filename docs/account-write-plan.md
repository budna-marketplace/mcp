# Budna account actions for MCP

**Implementation handoff · reviewed on 19 November 2026 · MCP main baseline `17fdb6e3b65f`**

Help a customer act through their existing Budna connection. Prioritize accurate listings, completed trades and customer control over commitments. Keep first-party control of identity checks, payment, physical proof, security settings and the notices that tell a customer what a connected app has done.

**Release status.** Public Explore and Account Read are the standard profiles. The `account-actions` profile implements the delegable verbs of every family below. It is live in Budna's development environment and, since 2026-11-19, in production for every account. Only deployment-enabled operations appear in the tool list, and each call still needs the relevant grant. Transaction flows were exercised in development. Production was verified without test writes: discovery, sign-in, account reads and permission step-up. The first released write, private watchlist membership, passed a signed-in check. See the coverage table below for what has been exercised. [Watchlist membership PR](https://github.com/budna-marketplace/mcp/pull/40) · [Account actions PR](https://github.com/budna-marketplace/mcp/pull/41)

**One explicit MCP-specific requirement.** First-party drafting can precede identity verification. For MCP, require current seller verification **before the first persisted listing**, including a blank draft or clone. Direct an unverified customer to Budna web, then check again. This rule changes listing eligibility only. Keep the established approval rules for bidding, publishing, ordering and payments.

## 1. Instructions for the implementing agent

Use §§2–4 as a product inventory and §5 to identify the reads each action needs. The 44 rows group related actions. The individual verbs, the actor, and the side effect determine eligibility and confirmation. For example, starting an automatic bid can place a bid immediately, pausing it leaves existing bids binding, and reading it does neither.

| Destination | Meaning for the implementer |
| --- | --- |
| **Direct** | The customer explicitly requests an approved action under a granted permission. Budna executes the request, records it and notifies the customer. This category includes some publicly visible or destructive operations. Show the actual effect in the tool description and annotations. |
| **App preference** | For designated bids and offers, honor the confirmation level the customer chose for this connected app in Budna. The default is confirmation in Budna. The other choices use the AI client’s approval or allow automatic execution within the customer’s limits. Above the applicable limit, Budna confirmation is required. |
| **Budna confirmation** | MCP submits the named action. The customer approves or declines the exact terms in Budna. On approval, **Budna executes the stored request once**. MCP reads the outcome. These commitments require Budna confirmation at every app preference level. |
| **First-party** | The person performs the action on Budna web or in the native app. MCP can explain the next step and read an allowed result. A handoff conveys no authority. |
| **Omit / Hold** | Omit staff/system effects, artificial signals and operations excluded by product policy. Hold a candidate when evidence of a supported customer action, required contract or safe implementation is missing. |

Before shipping a write family, reconcile **each verb** against the current owner-approved action inventory, the first-party customer workflow, the authoritative business rule and its tests. Record its business benefit, grant, actor/market, source and resulting state, allowed fields, existing reads, gates, approvals, side effects, retry behavior and recovery. Include unsupported variants and reasons. Ask the owner for a sanitized publishable contract wherever this repository lacks the wire contract. Do not infer a writable field or a new grant from a read schema. Keep unavailable verbs out of discovery. The proposed read names below are design examples.

Use first-party confirmation, privileges and account settings only within their approved meaning. If a team wants a second connection, new grant, new approval level, payment step, member delegation or an earlier release wave, document it for an explicit product decision before changing behavior.

## 2. Bringing supply onto Budna

Seller writes enter in Wave 3. **Direct** still requires an explicit customer request, a granted listing or selling permission, an eligible seller and the same business rules and notifications as the app. MCP additionally requires current seller verification before it persists a new listing, including a clone or relist. Unverified sellers can compose text, browse categories and complete verification on Budna web. Photo upload, paid placement and on-air hosting follow their own first-party boundaries even for a verified seller.

| ID and customer action | Destination | Required behavior and supporting reads |
| --- | --- | --- |
| S1 · Create, save or resume an owned draft, or create a similar draft | **Direct** for an ordinary draft. **First-party** for photo assistance or upload. | Resolve the personal or company seller and verify before creating a record. Create only a draft. Permit missing content or photos. Reuse safe fields from an eligible source to create a similar draft under the same gate. Exclude previous bids, orders, media associations, promotion and history. Resume an existing draft using its owner read. |
| S2 · Edit draft fields, replace attributes, set listing VAT treatment, discard a draft | **Direct** for supported owner edits and deletion. | Read the current revision, authoring rules and, for a company listing, permitted VAT choices. Ordinary edits cannot set status or quantity. Replace the full validated attribute set intentionally. Preserve unseen values or refuse a partial replacement. Separate single-attribute upsert stays **Omit**. Company tax registration and invoicing agreements stay **First-party**. |
| S3 · Publish one eligible draft now, or recover interrupted publication | **Direct** on the seller’s express request. **First-party** for any required upfront payment. | Recheck verification, account standing, terms, selling authority, readiness, category, required attributes, eligible image, limits and proceeds. ## 3. Buying, negotiating and completing a trade

These are product-approved destinations for future MCP actions. Each tool must derive the buyer, seller or dispute-party role from the connected account and the particular transaction. Use the existing Bids, Offers, Purchases, Orders and Ratings permission groups. Apply the marketplace’s current currency and eligibility rules to each action. A display currency or spending-limit currency does not authorize a trade in that currency.

| ID and action | Destination and authority | Terms, prerequisites and results |
| --- | --- | --- |
| B1 · Place one bid, including on an eligible live lot | **App preference** · Bids, buyer. | Show the exact binding bid, current round, minimum, increment, end time, fees and consequences of winning without paying. Check seller readiness, independent buyer, standing and eligibility again at execution. Bind to the actual live lot when applicable. An earlier automatic maximum can take priority and move the price or extend the deadline even when the caller’s bid is refused. Report the caller’s own outcome and fresh public state. A higher bid requires a new instruction. |
| B2 · Set or raise an automatic maximum, pause future bidding | **App preference** to set or raise. **Direct** to pause. Bids, buyer. | Show the private maximum and that setting or raising it can place a binding bid immediately. Check the limit against the authorized maximum. Pausing preserves bids already placed. Confirm eligibility separately for a live round. **Omit/Hold** manual bid retraction, a general delete, cap reductions and agent bidding loops. |
| B3 · Make, raise, counter, accept, decline or withdraw an offer | **App preference** to make, raise, counter, lower a seller counter or accept, as the eligible buyer or seller. **Direct** to reject or withdraw one’s own standing proposal. Show which proposal remains open, who can accept, quantity and the offered **total for all units**, currency, expiry and any additional fees/delivery costs. Placing an offer does not reserve stock. | B5 · Buy Now through checkout, including an auction with a Buy Now option | **Budna confirmation** · Purchases, buyer, for placing a **binding unpaid order**. **First-party** for the alternative reservation-and-pay flow, a new delivery selection or payment. **Omit/Hold** standalone basket or direct-purchase shortcuts. | Use a read-only quote where available. Keep payment methods, payment links, provider steps and payment initiation out of tools and receipts. |
| B7 · Cancel an eligible order, close an overdue unpaid sale, relist after closing | **Budna confirmation** · Orders, eligible buyer or seller to cancel, seller to close unpaid. **Direct** to relist an eligible already-closed item. | Read role, origin, funding/handover status, deadlines and legacy terms. ### Fields the agent may set

Use closed, operation-specific inputs. An owner read is a display view and can omit, truncate or redact values. Never generate a write from a whole `get_my_listing` response.

| --- | --- |
| Seller-entered listing fields | Bounded title, description, public tags, allowed category/condition and supported typed attributes. Expose only values the corresponding first-party edit actually accepts. |
| Sale and delivery terms | Use only the format-specific quantity, price, reserve, start/end or duration, and supported delivery/package selections for that state. Show seller net proceeds or labeled estimate where relevant. For eligible company listings, apply the approved per-listing VAT choice using that account’s invoice readiness. Company tax registration, invoicing agreements and seller/payment provider setup stay first-party. |
| Assets and identity | Read readiness and approved public references when needed. Let the user select, upload and manage media in Budna. Keep raw bytes, arbitrary URLs, local paths, signed credentials, precise addresses, contact data and physical codes out of tool inputs/receipts. |

For edits, define absent vs clear per field. Validate a precondition that prevents overwriting a newer web/mobile edit. Unknown keys, unsupported nulls and display-only complex values fail safely. Budna money stays `{"amount":"<exact decimal>","currency_code":"<ISO code>"}`. Preserve the documented currency and conversion rules. Budna timestamps are Unix epoch milliseconds unless the approved contract specifies another unit. Show the time zone for deadlines and schedules.

### Verification before listing creation

1. Before **any delegated operation that would first persist a listing**, derive the seller from the current grant. Apply the stricter MCP seller-verification requirement and the applicable shared eligibility checks. A historic verified flag, screenshot or self-attestation is insufficient. A connected company uses its own eligibility. A member’s personal verification cannot substitute.
2. If absent, expired or indeterminate, return a safe `verification_required` or appropriate blocked outcome and the approved **Budna web** destination. Create zero drafts, reservations or charges. Text composition, category research and authorized existing draft reads remain possible. Paid photo assistance and physical identity checks stay in their first-party flows.
3. The user signs in to Budna and completes verification there. Keep documents, national identifiers, credentials and codes out of MCP. The return is bound to the original account and confers no execution authority. A canceled, wrong-account or failed return leaves the request blocked. A client that cannot open a link can show first-party navigation instructions.
4. On a fresh user request, re-read eligibility and create once. Recheck the applicable publication requirements at publish time, including seller standing, current terms, category/attribute and media requirements, fee state and company/payout readiness where relevant. Verification does not publish, pay, or approve another action. Publication uses Budna’s direct-action policy when all gates pass.

## 6. Connect to existing Budna authorization and execution

**One customer connection.** Keep Public Explore credential-free over stdio and public HTTP. The authenticated resource remains `/account/mcp`. Use the existing connection, OAuth audience and incremental consent for released write permissions. Preserve the read-only configuration and old read-only clients. When writes are enabled, register a distinct **static** router/profile containing the permitted read and write tools on that same account resource. Existing grants do not acquire write permissions automatically. Enforce the same scope in the backend even when a client calls a tool it previously discovered. The public Marketplace Explorer never gains write authority, and a card selection never submits a transaction. [Existing account resource and permissions](account-access.md)

**Delegate only as the connected account.** Retain per-request token exchange, audience/issuer/expiry checks, exact client redirects, PKCE, immediate permission revocation and the existing connection lifetime. The resource server uses a short-lived scoped credential downstream. Keep service secrets in the deployment’s secret store, rotate them independently, and never persist a customer session or refresh token in the connector. A directly connected company acts as that company. A member login cannot select or impersonate a company by supplying its ID. Resolve ordinary target references as objects and recheck role, ownership and account standing. Keep the official first-party identity, company-admin and security flows accessible.

**Enforce first-party business rules at execution.** Use dedicated, allowlisted delegated commands calling the same authoritative product behavior as web/mobile. Trace checks and secondary effects currently attached to first-party request handling as well as the underlying operation. Confirm rules for verification, frozen/debt/terms restrictions, seller readiness, role, price floors, deadlines, cooling-off periods, membership, notification and attribution. Privacy projections, field permissions and shared rules must be enforceable at commit time. A frontend validator or an earlier eligibility read cannot serve as the guard.

| Step | Required behavior |
| --- | --- |
| 1 · Quote or check | A read observes state and has zero business effects. Show the current revision, terms, amounts, audience or deadline relevant to the requested action. Avoid exposing private limits, bidder identity and raw sensitive data. A quote never reserves stock, places a bid, publishes, creates an order or marks a message seen. |
| 2 · Submit one typed action | Validate closed inputs, conditions, scope, grant, actor and role. Identify the approved confirmation class for **that verb**. Submit one canonical request with a stable key through the existing action mechanism. Direct and eligible app-preference requests use that mechanism too. A real reservation or binding order is a distinct operation and cannot hide inside preparation. |
| 3 · Confirm where required | A pending action has **no marketplace effect**. Budna presents the actor, requesting app, target/round, exact text, quantity, amount/currency, time and effects. The signed-in customer may approve or decline. Designated bids and offers follow the per-app preference and per-currency customer limits across connected apps. The other covered commitments always require first-party confirmation. Expire a pending confirmation at the earlier of its approval deadline and the listing deadline, where applicable. Personal settings for levels and limits stay entirely in Budna. |
| 4 · Execute once at the authority | Approval causes Budna to recheck grant/scope, switches, ownership/role, verification, current state and terms, then claim and execute the stored request once. A material change fails or requires a fresh request/approval. No post-approval MCP commit tool. First-party-only actions such as paying an order have first-party submission and a separate status. |
| 5 · Report and recover | Read the stored action result. Return its safe reference, outcome, amounts and any separate pending/failed effect. A successful Buy Now action can leave an unpaid order. A pending approval, live listing, failed later add-on and unknown outcome have distinct meanings. After an interruption, reconcile against the existing action/domain state. Never place a second obligation to learn what happened to the first. |

Use HTTPS, strict Host/Origin/CORS, no-store and header-only credentials on the MCP resource. First-party approval pages require an authenticated session, CSRF protection, deliberate submission and binding to the correct account, grant, app and immutable terms. Link opens, GET, redirects, callback parameters and model-supplied confirmation flags grant no authority. For verification or approval, support an approved first-party destination and a text-only fallback. An elicitation response may open the destination. Only the action recorded by Budna can satisfy a requirement to confirm in Budna. Never relay a payment provider link, credentials, physical proof or arbitrary callback address. [MCP HTTP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) · [MCP elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation)

**Duplicates and concurrency.** Reuse Budna’s grant-bound durable action records and duplicate handling. For a tool that declares `request_id`, the MCP client creates one canonical, non-nil UUID per customer intent and retains it across reconnects and retries. For a quote-bound submission, reuse the quote and its exact arguments. The gateway forwards the same idempotency key on every transport attempt. Reusing a key with identical arguments returns the original outcome. Different arguments conflict. Also test a fresh tool call with the same canonical request inside the supported duplicate window. After renewal or a different grant, use the business record to reconcile ambiguous prior commitments. Do not promise cross-grant deduplication. Propagate the action’s stable identity to operations that support it. Unknown financial outcomes stay unknown until reconciled. Never retry them automatically. At execution compare draft, offer or round state, protect the last available unit and group membership across first-party and MCP writers, and account for partial side effects. Bound retries, deadlines, request/response bytes, concurrency, polling, pending approvals and per-app/per-user write budgets.

**Outputs and operation.** Supply structured results and an output schema, closed inputs with runtime validation and readable text fallback. Use HTTP 401/403 OAuth challenges for authentication/scope. Expected validation, eligibility, stale terms, ownership and business failures are tool errors with `isError: true` and a safe next step. Foreign objects are indistinguishable from missing ones. Treat marketplace text as untrusted and reject disallowed control characters in submitted user text. Set `readOnlyHint` false on every write and use conservative `destructiveHint` for operations affecting people, commitments or money. Set `idempotentHint` according to actual replay behavior, including side effects, and `openWorldHint` for marketplace interaction. Hints do not enforce policy. [MCP tool semantics](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

Use existing first-party action history, receipts, protected user notifications and stop controls. Keep the user informed even when they configured direct execution. Check in-app notices for executed actions, push for commitments, confirmation requests and failed approved actions, and first-party security notices for new connections and changes to confirmation levels or limits. Ensure delegated tools cannot dismiss or mute security/connected-app notices. Keep evidence of approved terms and action origin in first-party systems under existing audit/retention rules. General logs contain bounded operation/outcome/duration only, never tokens, private identifiers, names, raw URLs, text or payloads. Reserve stdout for MCP frames.

## 9. Handoff release gate

- **Product and Trust** reconcile the verb inventory against the current first-party policy and record any requested departure. The requested verified-before-draft rule needs explicit coverage wherever a delegated action can create a listing. Do not reopen settled confirmation, payment or company boundaries by inference.
- **Identity and marketplace owners** confirm the enabled scopes/client policy, authoritative shared checks, idempotency and status behavior, first-party return destinations, fee timing and state transitions. - **Commerce and Support** own recovery for unknown commitments, missed payment deadlines, returns, disputes, false reports and partial completion. Leave a first-party route to a human when the grant is revoked or a right cannot be exercised through MCP.
- **Release owner** records one disposition for every first-party customer action in the reviewed family, including omitted and first-party-only verbs. Require zero unclassified actions in that family, a matching published tool/permission list, evidence for each enabled write and an operational rollback drill. An implementation is ready when the approved journey can actually be completed and recovered.
